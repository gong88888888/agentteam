# Agent Team 设计审查与持续迭代优化报告

日期：2026-11-18。性质：现有设计审查与改造提案，尚未实施到另一台电脑的系统。

## 1. 核心判断与审查边界

这套设计具备角色分工、变更审批、缺陷复测、知识沉淀的基础意识；v3 进一步提出功能切片、依赖图、上下文包、证据失效和事件账本，方向可以保留。

但目前文档对“如何完整理解原始需求”“如何证明真实产品可用”“交付后由什么事件继续推进项目”的约束不足。流程即使顺利走完，也可能交付一个严格符合不完整 PRD 的产品。增加角色、并发度、知识库容量，无法单独消除这个问题。

你描述的四个现象可以连成一条待验证的因果链：

> 原始材料遗漏或被摘要压缩 → 产品与设计基准不完整 → 开发围绕缺失基准实现 → QA 围绕同一基准验证 → 阶段全部完成但用户任务失败 → 复盘归档后无新任务调度 → 项目停止改进。

其中，规则缺口和冲突可以从本地材料确认；另一台电脑是否沿用了这些实现、实际失败比例及模型能力是否成为瓶颈，尚不能确认。

本次读取的材料：

| 材料 | 内容与本次结论 |
|---|---|
| `agentteam1.md` | 12 类角色、阶段流转、协作与人决策规则；覆盖职责，尚未构成可运行的团队协议 |
| `agentteam2.md` | 12 类角色提示词；有输出模板，缺少来源追踪、工具行动和语义验收的细化要求 |
| `agentteam-cluster-v3.md` | 切片、DAG、四层知识、证据与增量验证；应成为整合方向，但不能当作已实现能力 |

| `RAG-Agent-Toolkit.zip` | 读取清单、README、ARCHITECTURE，以及 controller、validator、documentParser、aiTool 等关键源码；仅是局部源码审查 |

## 2. 对你提出的问题逐一回答

### 2.1 为什么任务完成率不高？

首先要区分三种完成：模型返回了结果、任务产物通过验证、用户目标已经达成。当前落地参考对前两者的区分不够明确。

它在第 155—182 行附近，把首批 Agent 的实现归纳为拼接 Prompt、调用模型、结构化校验、写文件、返回状态。这里没有详细规定 Agent 如何启动服务、调用真实接口、检查数据、使用浏览器、读取失败日志并继续修复。若实现只照此封装，输出代码或测试报告就可能被视为任务完成。

另外，大任务一次生成、交接时只传摘要、缺少可测前置条件，会使下游集中遇到上游积累的问题。v3 的切片与就绪检查已经针对其中一部分给出方向，应核验是否真正落地。

建议先按最近失败任务分类：需求缺失、设计缺失、实现错误、契约漂移、环境失败、工具不可用、验证不足、等待决策、预算耗尽。各类分别统计，避免把所有失败都归因于“模型不够强”。

### 2.2 为什么产品和设计角色解析文档不足？

产品提示词要求产出定位、功能、非目标、场景和验收指标，但没有强制逐段登记原文、建立需求 ID、记录冲突、回查遗漏。它允许生成一份结构完整的 PRD，却不要求证明 PRD 完整保留了输入文档。

设计角色主要输入产品基准，不强制读取相关原始材料。产品漏掉的权限、状态、表格规则或异常流程，会继续从设计里消失。设计交付模板强调页面、视觉规范和还原度，业务状态与跨页流程覆盖没有独立门禁。

还存在明确的规则风险：`agentteam2.md:74` 和 `:102` 允许产品自行“砍掉无价值功能”，但同文件又禁止批准范围变更。对价值的主观判断可能被误用为删减用户明示需求的权限。

解决方式是建立“原文→需求→场景→设计状态→验收”的追踪表，并让 QA 或评审角色回看原文独立找遗漏。仅给产品提示词增加“认真阅读、深入理解”无法检查其是否真的读全。

### 2.3 为什么执行一轮以后效果差、bug 多？

当前设计已经要求异常测试、回归和缺陷复测，不能简单说它“没有测试”。问题在于测试是否独立、是否执行、是否验证真实链路。

如果 PRD、代码和测试都从同一份有遗漏的摘要生成，三者可能互相一致，但同时偏离用户需求。仅有编译成功、JSON 合法、报告写着通过，也不足以证明真实接口、权限、持久化和多页面操作正确。

应在开发前审查验收标准，在每个小切片内运行真实服务，并在切片集成后检查跨模块业务流程。产品要判断用户是否完成目标，设计要查看实际界面和交互，QA 要给出真实执行记录。

### 2.4 为什么角色没有像项目团队一样持续优化？

原设计的最终路径是“发布→归档→复盘→项目闭环”（`agentteam1.md:409` 起）。虽然复盘角色要求跟进措施，但没有定义行动项如何创建任务、进入队列、绑定下一轮、何时唤醒负责人、怎样再次验收。

v3 补充了实时知识与执行中的反馈，但仍以一次交付收口为主，没有完整定义项目跨迭代的生命周期。

角色不会仅因被命名为产品经理或复盘工程师，就在一次模型调用结束后持续工作。持续推进必须由运行中的调度服务、持久化任务和事件触发承担。电脑或调度进程关闭时只能保留待办，不能承诺继续执行。

需要两条不同的反馈链：

- **产品迭代链**：反馈/缺陷 → 分类 → 产品与设计修订或开发修复 → 验证 → 当前迭代完成 → 下一迭代。
- **团队改进链**：重复根因 → 改进任务 → 修改检查项、模板、测试或提示词 → 对照评测 → 生效并观察复发。

知识入库提供可用信息；任务入队和再次调度才会产生后续行动。

### 3.1 压缩包中已验证的局部问题

未安装或启动宿主项目。直接读取 ZIP 中原始 `harness/validator.js`，使用本机 Node v20.11.1 执行其独立校验逻辑，得到：

| 输入 | 实际结果 | 说明 |
|---|---|---|
| 校验器名称不存在 | `{valid: true}` | 校验配置拼错也放行 |
| `jsonValidator` 输入字符串 `null` | `{valid: true}` | 只证明可以 JSON.parse，未证明满足结果契约 |
| `fileValidator` 输入不存在的非空路径 | `{valid: true}` | 不检查存在性、内容、格式或可用性 |

这三个行为已局部复现；它们是否影响实际 Agent Team，取决于另一台电脑是否复用了该模块及怎样配置。

另外，静态读取 `harness/controller.js` 可见任务主体放在内存 Map；写日志本身不构成重启后恢复任务。`mcp-tools/lib/documentParser.js` 的 PDF/DOCX 路径以文本提取为主，未在这些函数中看到页级证据、图表语义或扫描件 OCR 回退。此处只能认定这些函数的能力边界，不能据此断言整个宿主平台不存在相关能力。

### 3.2 原有修复建议需要修正的地方

1. **不能彻底排除 LLM 发现的问题。** `修复建议1.md:33` 建议 LLM 问题清单不参与放行判定。这样工具未覆盖的业务错误、需求遗漏、体验缺陷可能被忽略。应取消 LLM 自行宣称成功的放行权，但保留有证据的阻塞意见；未解决的严重问题进入门禁阻塞，误报通过复验或有记录的裁决处理。
2. **确定性门禁不能独立判定全部产品质量。** 程序能检查版本、证据、必填字段、测试结果和未结问题；需求语义、交互可用性仍需有依据的专业审查与必要的人验收。
3. **审批权限存在冲突。** 旧提示词和 v3 要求 L2/L3 人审批；修复建议 `:274` 又允许技术负责人批准 L2。应先保留既有人的审批权；如需委托，单独明确可委托范围和身份，不能靠角色自行解释。
4. **基准冻结应允许修正错误。** 冻结用于版本追踪，不能让错误 PRD 永久成为唯一事实。原文新证据或需求冲突应创建变更提案，批准后更新基准并使相关结果失效。
5. **重试耗尽不等于超时。** `FAILED_DEADLINE` 不宜承担所有失败语义。区分重试耗尽、实际截止时间超时、预算耗尽、取消和等待决策，以便恢复策略正确。
6. **多起点 DAG 可以合法。** “所有节点从同一个起点可达”可通过虚拟根实现；不能把合法的独立准备任务直接当错误。持续迭代在 DAG 外生成下一轮计划，单轮内部仍保持无环。
7. **证据指纹应按生产链确定。** 涉及 LLM 的语义判断记录模型、提示词、输入和上下文版本；纯构建证据记录实际代码、依赖、命令、工具与环境。不能把所有无关提示词修改都当作所有证据必须作废的原因，也不能漏掉真实依赖。
8. **固定 24 小时审批过期不宜作为通用要求。** 优先绑定产物版本、范围与环境；仅对有时效要求的操作配置有效期。
9. **“非目标不测试”应收窄。** 不为排除的功能补做完整功能测试，但仍需验证它不会被意外启用，也不能豁免已有范围的权限、兼容与回归检查。
10. **提示词优先级需要改写。** “通用约束高于任何任务指令”应限定为应用内部政策，不能越过运行平台的系统规则或用户明确授权；产品文档和检索内容属于数据，不能自动成为工具执行指令。

此外，修复建议中关于实际系统读取 `fatal: 0`、特定函数和既有故障的陈述，当前目录没有相应完整源码支持。这里将其作为待验证假设，不当作本次已观察到的事实。

## 4. 三种改造路线

| 路线 | 做法 | 优点 | 局限 |
|---|---|---|---|
| A：提示词补丁 | 补产品、设计、QA 的来源、状态和验收要求 | 修改小，适合快速试验 | 调度和验证不变时，无法保证后续行动 |
| B：保留框架，补可验收切片与迭代控制（推荐） | 整合 v3，优先实现来源账本、真实验证、缺陷路由与下一轮调度 | 能逐步接入已有实现，收益可测 | 需要改任务模型、上下文和门禁 |
| C：整体重写 | 重建调度、执行、工具和存储 | 可以统一协议 | 当前没有运行证据支持必须推倒重来，迁移风险较大 |

建议先采用 B，并用 A 作为其第一批改动。只有在实际代码审查证明底座不能支持可靠状态和工具执行时，才考虑 C。

## 5. 产品和设计如何读懂文档

### 5.1 文档接入：保留结构和来源

先为输入文件生成清单：文件 ID、版本/内容哈希、类型、页数或章节、解析状态、表格/图片数量及告警。对扫描件、图表密集页或提取异常页补充视觉读取/OCR，不把空白文本自动解释为没有需求。

把原文整理为可追踪单元，保留章节、段落、页码/坐标或表格单元位置。不能先把全部材料压成一份摘要再丢掉原文。

每个原文单元都应有处置：映射到需求、作为背景/示例、确认为重复、经授权排除、存在冲突、解析失败或待澄清。未处理单元必须可查询；“已经阅读”不是覆盖证据。

### 5.2 产品提取：先理解再限定范围

每条原子需求至少包含：

| 字段 | 要回答的问题 |
|---|---|
| `requirement_id / source_refs` | 哪条原文支持这项需求，使用哪个版本？ |
| 用户、目标、触发和前置条件 | 谁在什么情况下要做什么？ |
| 业务规则与数据约束 | 哪些输入、条件和结果合法？ |
| 正常、异常、边界、权限场景 | 哪些情况下不能照正常流程走？ |
| 验收项及可观察结果 | 怎样判断用户真正完成任务？ |
| 优先级与依赖 | 影响哪些功能片？ |
| 事实/假设/待决策状态 | 哪些由原文明示，哪些尚未确认？ |

原文没有定义的行为应登记为假设或问题，不能伪装成明示需求。可以提出推荐方案，但不能因“价值不高”擅自移除用户要求。

非目标清单在理解输入与确认范围后形成；不再要求在读全材料前优先压缩范围。影响目标、数据、权限、范围或核心契约的未决问题必须解决后才能实现相关切片；无关切片可以继续。

### 5.3 设计覆盖：从场景到状态

设计者读取已确认产品要求，同时读取相关原文、业务规则、权限与数据约束。每个用户场景应映射到页面/组件、状态、操作、反馈、跳转和验收项。

按场景适用性检查：首次进入、有数据/无数据、加载中、提交中、成功、失败、超时、重试、输入不合法、无权限、会话失效、重复提交、刷新/返回、数据过期或冲突。无需对每个页面机械增加全部状态，但不适用必须有理由。

视觉规范、响应式、可访问性仍保留。深色模式、快捷键等按产品范围决定，不自动作为所有产品必须增加的工作。

### 5.4 独立反向审查

产品提取完成后，由 QA 或评审角色从原文反向寻找未覆盖条目，而不是只看 PRD 自检；设计完成后，再检查每条用户路径是否存在可执行的状态和反馈。

程序校验引用有效、ID 唯一、关联不悬空、必填关系齐备；专业审查判断映射是否正确。关系数量齐全不能自动证明语义正确。

> 原文片段 → 需求 REQ → 场景 SCN → 设计 UI → 接口/API 与代码 → 验收 AC → 执行证据 EV。

这条链应支持反向查询：失败的验收项影响哪条需求；改动一段原文需要重查哪些设计、实现和用例。

### 5.5 RAG 的使用边界

首次建立需求账本必须按章节/结构遍历全部材料，并核对未处理单元。只做 top-k 相似检索，不能证明需求已经完整读取。

RAG 适合给执行中的具体任务补充相关原文、契约、历史缺陷；它不能替代首次覆盖审计。当前权威规则按 ID/版本准确加载，不依赖“相似度足够高才出现”。上下文包中的引用必须可访问，并记录实际读取结果。

## 6. 团队执行与真实验收

### 6.1 保留职能，按任务唤醒

保留现有产品、设计、架构、开发、QA、评审、安全、运维和复盘职责。角色名称不决定需要多少常驻实例；先降低同时开发量，确保验证能跟上。

调度、版本比较、计数、权限检查、证据登记交给确定性程序。LLM 承担需求理解、设计、实现、问题发现和原因分析。安全判断等专业工作不能因为角色瘦身而无人负责。

每个切片设置产品负责人和实现负责人；产品/设计对实现后的用户流程继续负责，不能交完文档即退出。

### 6.2 每次交接提供任务包

任务包至少包含目标、范围、需求/场景/验收 ID、原文引用、有效基准与契约版本、当前代码版本、既有失败、未决问题、允许写入范围、依赖、验证方式和预算。

接收者先核验输入能否读取、是否足够、是否过期，再决定开始或返回具体缺口。不能仅靠“详见产品文档”完成交接。

### 6.3 Agent 需要执行循环

建议运行协议：读取当前任务与版本 → 检查就绪 → 执行一小步 → 调用相应工具 → 观察结果 → 定向修复 → 提交产物与证据。

开发需要读写代码、构建、运行及查看日志；QA 需要真实接口、测试环境及浏览器等适用工具；设计需要查看实际渲染；产品需要核查用户路径与业务结果。工具无法使用或环境未就绪，应标记阻塞，不能改成口头模拟测试。

### 6.4 将“完成”改成可检查条件

单个功能片完成至少满足：

1. 相关原文需求和已批准范围都有对应验收项，关键歧义已解决。
2. 设计覆盖适用的业务状态，实现与当前契约一致。
3. 应用在目标测试环境可运行，相关真实接口、权限与数据行为通过检查。
4. 必需测试有执行结果和有效证据；mock 测试清楚标记，不充当真实集成证据。
5. 产品确认用户目标、设计核查真实界面、QA 独立复验；不存在未处理的阻塞问题。
6. 必需代码、运行说明、迁移/回滚材料已随版本更新。

非阻塞问题可按明确政策进入后续 Backlog，不能为了“零缺陷”隐藏、删单或擅自降低等级。未知、跳过、阻塞均不得计为通过。

证据记录对象版本、验收项、命令/操作、环境、结果、日志或截图、生产者、时间及失效条件。证据证明实际执行过什么，不只记录一个 PASS 字符串。

程序门禁聚合客观证据、专业评审和未结问题。涉及人的既有审批仍保留；不要用自动评分替代范围与发布决策。

### 6.5 缺陷回到正确的负责人

| 问题类型 | 首要责任 | 处理链 |
|---|---|---|
| 明示需求遗漏或理解错误 | 产品 | 修订需求提案→批准→设计/实现/用例影响分析 |
| 交互缺失、状态错误、实际难以完成操作 | 设计 + 产品 | 补设计/验收→开发→真实界面复验 |
| 契约或架构冲突 | 架构 | 契约裁决/变更→通知受影响切片→回归 |
| 实现不符合有效基准 | 开发 | 复现→修复→适当回归→QA 关闭 |
| 环境、数据、部署问题 | 运维/执行服务 | 恢复环境→重跑受影响验证 |
| 重复问题、规则无效 | 复盘协调负责人 | 建改进任务→改检查/测试/流程→评测 |

不应把所有 bug 自动派给开发。任务关闭权也不等于开发声明修复：修复后进入待复验，QA 根据有效证据关闭。

## 7. 让团队持续经营同一个项目

### 7.1 分开项目、迭代和任务

- 项目状态：活跃、等待决策、用户暂停、已归档。某个版本完成不自动归档项目。
- 迭代状态：候选、已计划、执行中、验证中、已完成、已取消。
- 任务状态：草稿、就绪、执行中、待验证、需整改、已完成；另有阻塞、待决策、失败、取消。

单次运行因预算结束，应明确报告仍未完成的事项，并保留检查点。项目是否活跃与本轮是否还可继续消耗预算是不同问题。

### 7.2 引入迭代控制器

它可以是现有调度器的一部分，不必增加一个常驻管理 Agent。职责包括：

1. 接收 QA 缺陷、产品/设计走查、用户反馈、运行告警、批准的变更和复盘行动项。
2. 去重并分类为缺陷、需求澄清、优化建议或团队改进。
3. 对已批准范围内的修复创建可执行任务；新增目标和范围变化整理为决策包。
4. 按阻塞程度、用户影响、风险和依赖排队，为验证预留容量。
5. 当前迭代验收后，从已批准的 Backlog 生成下一轮；无就绪任务则保持可唤醒的空闲状态。
6. 遇到预算耗尽、用户暂停或需要授权时停止相应执行，并保留原因与恢复条件。

“持续优化”指在既有目标、授权和预算内持续处理已知工作，不表示无限运行或擅自创造功能。没有可信收益证据的新想法先作为候选提案。

### 7.3 行动项必须入队

复盘产出不能只是一段建议。每个行动项需要 `action_id`、根因/缺陷引用、负责角色、目标迭代、触发条件、完成定义、验证方式和状态；创建后返回调度器实际生成的任务 ID。

是否改进成功取决于验证和后续复发观察，不取决于写过多少总结。产品文档、设计状态、代码、回归用例、经验条目应随同一任务更新；不涉及的产物注明原因即可。

### 7.4 改进团队规则需要评测

缺陷修复与修改提示词是两件事。同类根因再次出现时，检索历史并判断原因是没检索到、没有遵守、规则本身错误，还是验证漏检。只在原因支持时修改对应环节。

优先把稳定规则变成可执行检查或回归用例；提示词变更记录版本、适用任务和对照结果。新经验先进入候选状态，复核后再用于指导后续任务，不自动覆盖已批准基准。

## 8. 角色规格修订建议

以下是供后续整合的行为条款草案，不代表已替换现有提示词，也不构成完整 Schema。

| 角色 | 必须新增的行动 | 必须提交的产物 | 不能宣称完成的条件 |
|---|---|---|---|
| 产品 | 遍历原文、登记来源、区分事实与假设、独立遗漏审查、实现后走查 | 需求账本、来源覆盖表、场景/验收映射、待决策清单 | 存在未处置原文单元或影响本片的关键歧义 |
| 设计 | 读取相关原文、建场景状态表、查看实际产品 | 状态/交互规格、需求映射、视觉产物、实现差异清单 | 核心场景无可执行交互，或未查看实际结果却声称还原达标 |
| 开发 | 检查版本、逐片实现、运行与修复、提交影响范围 | 代码版本、执行记录、相关测试、未解决问题 | 仅输出代码文本或未经验证的成功说明 |
| QA | 从原文和验收独立设计用例、真实执行、缺陷复验 | 用例及实际结果、缺陷、证据、覆盖缺口 | 必需检查未知/未执行，或严重缺陷仍未关闭 |
| 评审 | 找遗漏和反例，区分阻塞与建议，复核整改 | 有位置/依据的发现、严重度、处置状态 | 只评风格而未覆盖本任务关键风险 |
| 总指挥/迭代控制 | 基于账本推进，确保行动入队，处理决策与停止条件 | 当前目标、就绪队列、阻塞清单、下一轮计划 | 仅因所有 Agent 都返回过结果就结束项目 |

可追加到产品角色的关键约束：

> 对每个输入单元记录去向；每项需求引用具体来源与版本。原文没有说明的行为标为假设或待确认。不得因自行判断价值而删除明示需求。提交前从原文反向核查遗漏；收到实现反馈后，持续维护需求与验收的有效版本。

可追加到设计角色的关键约束：

> 每个核心场景均定义页面、适用状态、操作、反馈、恢复路径及验收项。读取相关原文而非仅依赖产品摘要。提交设计时列出未覆盖场景；实现后查看真实界面，提交差异与可执行整改项。

可追加到 QA 角色的关键约束：

> 原始需求是独立核查依据。只报告实际执行的测试；记录环境、版本、步骤、预期、实际和证据。未执行、阻塞、跳过与通过分开。发现基准遗漏或设计问题时创建对应类型的问题，不一律归为代码 bug。

这些约束需同时得到任务字段、工具和门禁支持；只追加文字属于路线 A，不能保证完成路线 B 的效果。

## 9. 最小案例：从漏需求到持续迭代

示例原文要求：“普通成员只能查看自己的任务；管理员可以查看全部任务；提交失败后保留已填内容。”这是本报告构造的说明案例，不是项目中的真实需求。

产品不能只提取“任务列表、任务提交”两个功能。应建立权限与失败恢复的独立需求，并分别映射验收项。设计应包含普通成员/管理员视图以及提交失败后保留输入、显示原因并允许重试的状态。

实现验收至少检查：普通成员调用真实接口也无法读取他人数据；管理员能看到正确范围；模拟提交失败后输入仍保留，恢复网络后可重试；刷新和持久化行为按已确认规则验证。

如果产品未提取权限要求，QA 应从原文发现遗漏并回流产品；如果设计已有失败态但页面丢失输入，则回流开发；如果大家都未读到原文相关页，创建文档接入或覆盖审计改进任务。

本轮修复验证后，将回归用例和有效经验登记。下一轮接到相同模块任务时自动加载这些约束；项目保持活跃，继续处理已批准的待办，而不是归档一次后失去上下文。

## 10. 实施顺序和每批验收

不在没有代码与任务规模依据时承诺工时，以每批可复验结果决定是否继续。

| 批次 | 改造范围 | 验收方式 |
|---|---|---|
| 0：采集基线 | 固定一个真实输入和一个失败运行，保存输入、各角色输出、工具记录、代码、缺陷、模型/提示词版本 | 能解释每个失败发生在哪次交接、哪条验收及哪个版本 |
| 1：先补理解 | 来源清单、需求账本、设计状态表、QA 原文核查；修正擅自删需求规则 | 人工预置一条藏在表格/末尾的关键要求和一组冲突，系统能指出来源与处置，不静默丢失 |
| 2：证明可用 | 工具执行循环、真实环境、有效证据、完成定义、缺陷定向回流；如复用 ZIP 则先修宽松校验 | 不存在文件、未运行测试、错误版本、关键场景失败均不能放行 |
| 3：跨轮推进 | 项目/迭代分离、反馈事件、行动项入队、预算和唤醒条件 | 首轮后注入一个已批准范围内缺陷，系统自动建任务、调度、修复、复验并更新产物 |
| 4：记忆和恢复 | 持久化状态、上下文重建、经验复核、证据失效 | 重启后保留待办；改变需求或代码后受影响结果转待复验；重复事件不重复产生副作用 |
| 5：再扩并发 | 整合 v3 切片 DAG、工作树与契约、限制在制品、验证资源配额 | 任务吞吐提升且需求漏项、冲突、逃逸缺陷未增加，再扩大并发 |

这一路径可以沿用 SQLite、文件产物和现有框架。是否需要向量库或图数据库，由真实检索需求决定；当前优先做准确的来源、状态和任务关联。

先统一协议文档：以 v3 为架构方向，纳入已修正的证据/状态建议；把旧文档相应条目标为替代或废弃。不要继续把多套“最高优先级铁则”无差别拼进同一个系统提示词。

## 11. 如何验证优化有效

### 11.1 指标必须包含真实交付效果

| 指标 | 定义 |
|---|---|
| 原文处置率 | 已记录处置的输入单元 / 所有需审查输入单元；排除必须有理由与权限 |
| 需求召回率 | 独立人工标注关键需求中，被正确提取的比例；不能用系统自己提取的列表作分母 |
| 设计场景覆盖率 | 已有有效交互规格的必需场景 / 独立确认的必需场景 |
| 用户任务成功率 | 在目标环境通过独立验收的用户任务 / 本轮承诺用户任务 |
| 首次验收通过率 | 首次提交即满足完成定义的切片 / 已首次提交的切片 |
| 逃逸缺陷 | 验收通过后发现的缺陷，按严重度与迭代记录 |
| 复发率 | 已修复并总结的根因，在后续相关任务中再次出现的比例或次数 |
| 行动闭环率 | 到期且已验证有效的行动项 / 到期行动项 |
| 成本与等待 | 每个验收通过切片的耗时、Token、工具成本、人工介入和排队时间 |

不要把拆出更多小任务导致的完成数量增加当成完成率提升。任务生成后应保留原始承诺范围，取消、降级和排除单独报告。

### 11.2 最小评测集

准备至少六类材料：短而明确的需求、长文末尾包含限制、表格/图示承载规则、版本冲突或歧义、已有项目增量变更、首轮交付后的缺陷与反馈。

固定输入、初始仓库、模型配置、工具、预算及人工介入政策，比较旧协议与新协议；每种条件尽量重复运行至少三次，记录波动。小样本用于筛查明显问题，不能据此承诺普遍提高多少百分比。

验收由预先准备的关键需求清单、真实执行结果和独立审查组成，不采用同一 Agent 事后给自己评分。主观体验可用明确任务和评价标准辅助人工判断，不伪装为全自动客观分数。

### 11.3 必须做的失败注入

- 缺少或拼错验证器：应拒绝或明确阻塞。
- 返回不存在的文件、空产物或不符合业务契约的合法 JSON：应失败。
- 有测试报告但无真实执行记录：不得通过必需测试门禁。
- 原文有关键条款但 PRD 未包含：原文反向核查应发现。
- 前端 mock 通过、真实后端字段或权限不符：集成验证应失败。
- 验收后修改代码/需求：受影响证据失效并重新排队。
- 缺陷源于需求或设计：派发到正确角色，不只重试开发。
- 进程重启或同一事件重复投递：任务可恢复，已完成副作用不重复执行。
- 复盘产生行动项：必须可查实际任务 ID，并能在预算内继续调度。
- 预算耗尽或无授权新需求：保留未完成状态，不宣称成功，不无限运行。

## 12. 本次已完成与后续核验边界

已完成：五份设计材料的审查、压缩包关键模块的局部源码检查、校验器三项行为验证，以及本报告中的根因分析、角色修订、执行/迭代方案和评测设计。

未完成且未声称完成：另一台电脑的源码核验、模型效果对比、真实产品端到端运行、缺陷修复和生产发布。本次未修改原设计文档或压缩包，未将提案视为用户已批准的运行政策。

后续最有价值的核验对象是一组完整失败样本：原始产品文档、产品/设计输出、任务状态与工具日志、最终代码和用户观察到的具体失败。用它追踪“要求在哪里丢失、失败在哪里被错误放行、哪项改进没有进入下一轮”，再按第 10 节顺序改造。
